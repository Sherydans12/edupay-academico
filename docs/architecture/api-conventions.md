# API conventions

Status: proposed contract baseline for NestJS API review

## Style

Use versioned REST/JSON as the default for the MVP unless an approved ADR selects another style:

- base path: `/api/v1`;
- resource-oriented URLs and HTTP semantics;
- OpenAPI generated from the NestJS API;
- request validation at the boundary;
- stable internal IDs exposed as opaque identifiers.

This is a convention proposal, not an implementation directive until [ADR-0008](../decisions/ADR-0008-api-and-contract-versioning.md) is accepted.

## Request context

- Authorization uses the Identity-issued access token/session contract.
- The server resolves tenant context from authenticated membership/session context.
- A client `tenantId` is not trusted for authorization.
- Every request has a correlation/request ID, generated by the edge if absent and propagated internally.

## Data conventions

- JSON field naming is consistent across API and web client; choose camelCase or another convention once and apply it everywhere.
- Timestamps are ISO 8601 with explicit offset; storage uses the approved canonical timezone strategy.
- Enumerations are stable strings, not database ordinals.
- Pagination is cursor-based for potentially large collections; small bounded lists may use a documented page shape.
- Sort/filter capabilities are explicit per endpoint.
- Mutation endpoints document idempotency behavior.

## Error envelope proposal

```json
{
  "error": {
    "code": "SUBMISSION_DEADLINE_INVALID",
    "message": "The submission could not be accepted.",
    "details": [],
    "requestId": "..."
  }
}
```

Messages should be safe for end users; diagnostic details belong in logs. Validation errors should identify fields without exposing internal schema or tenant data.

## Endpoint families

The exact route list belongs in the API contract, but the families are expected to include:

- identity/session context;
- tenant and membership context;
- academic years, courses, students, teachers, subjects, enrollments;
- learning units and learning items;
- file upload intents and metadata;
- submissions, revisions, reviews, and change requests;
- notifications;
- integration/sync status for authorized operators.

## Contract requirements

- A successful response and error response are documented.
- Authorization behavior is documented per endpoint.
- Cross-tenant and lifecycle edge cases have tests.
- API changes are backward-compatible within a version or deliberately versioned.
- Provider-specific IDs are not required for normal client behavior.

## Unresolved decisions

- Exact JSON naming convention.
- Cursor format and standard pagination envelope.
- Whether Zod schemas are shared between frontend and backend or generated from OpenAPI.
- Whether API clients are generated or hand-written.
- Idempotency-key requirements for uploads, submissions, and sync triggers.
