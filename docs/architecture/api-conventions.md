# API conventions

Status: reconciled contract baseline for the Académico API and EduPay Identity integration

## Style

Use versioned REST/JSON as the default for the MVP:

- base path: `/api/v1`;
- resource-oriented URLs and HTTP semantics;
- OpenAPI at the API boundary;
- request validation at the boundary;
- stable opaque IDs exposed to clients.

## Shared application contracts

Shared application request and response contracts belong in
`packages/contracts`. When a request or response shape crosses the web/API
boundary, define it with Zod 4 there and derive TypeScript types with
`z.infer`; do not manually duplicate interfaces in the frontend and backend.
The frontend may import `@edupay/contracts`, but it must never import API
implementation files. The backend may adapt shared schemas at its HTTP
boundary while keeping domain and application models independent from
transport DTOs. Prisma models are persistence models, not API contracts.

OpenAPI remains the externally inspectable API documentation at the API
boundary. The MVP does not require code-generation infrastructure. The first
frontend integration uses a thin hand-written API client.

Académico JSON request/response fields use camelCase. This does not rename Identity JWT claims: the Identity token contract uses `tenant_id`, `membership_id`, and the other claim names documented in [identity model](identity-model.md).

## Identity integration contract

Académico trusts only access tokens issued by EduPay Identity for the configured audience. The adapter must:

1. obtain Identity signing keys from `GET /.well-known/jwks.json` and support bounded key-rotation overlap;
2. validate signature, `iss`, `aud`, `exp`, `nbf`, acceptable clock skew, and required claim shape;
3. require `sub`, `sid`, `tenant_id`, `membership_id`, and `roles` for tenant-scoped work;
4. treat `tenant_id` as the canonical ecosystem tenant ID and create a request-scoped tenant context from it;
5. apply Académico’s role/resource rules after token validation;
6. use the restricted Identity session/membership status contract for high-risk actions when current status is required.

The access JWT has a maximum lifetime of 10 minutes. Role and membership claims are an issuance-time snapshot; they do not replace current academic authorization. Refresh tokens, token families, session revocation, and refresh reuse handling are owned by Identity. Académico never stores credentials or refresh tokens.

Membership/tenant switching is performed by Identity through `POST /api/v1/auth/sessions/current-context`. Identity verifies that the requested membership belongs to the authenticated user and is active, then issues a new access token. A client cannot grant itself context by sending `tenantId` or `membershipId` to Académico.

The existing EduPay administrative login is a separate trust domain. Académico does not accept its cookies or credentials through this contract and does not assume migration or federation.

## Request context and tenant selectors

- The server resolves trusted tenant context from validated Identity membership claims, not from client input.
- In Académico API JSON, `tenantId` denotes the canonical ecosystem tenant ID when a target selector is needed. It is a selector at most and is never authorization context.
- A URL, body, query string, header, or hidden form `tenantId` that conflicts with trusted context must be rejected or ignored according to the endpoint contract; it must never widen scope.
- A request without an active tenant context fails closed for tenant-owned data. `SYSTEM_ADMIN` without explicit audited elevated support context has no automatic tenant access.
- Every request has a correlation/request ID, generated by the edge if absent and propagated to Identity calls, academic audit, and provider operations.

## Academic linking contract

EduPay Académico explicitly initiates Student/Teacher ↔ IdentityUser linking. The academic API owns the link mutation on its record and calls Identity only through a restricted service-to-service lookup contract such as `POST /internal/v1/identity-users/resolve`.

The link request must be authenticated, actor-attributed, tenant-scoped, exact, auditable, and idempotent where retries are possible. Identity returns minimum necessary data only. It must not be used for unbounded directory search, name-only matching, automatic linking from an unverified email, credential access, or token access. One verified email maps to one Identity user globally; institutional usernames are unique within a tenant realm after safe normalization.

## Identity endpoint dependencies

The Académico adapter may consume these Identity contracts:

| Contract | Use |
| --- | --- |
| `GET /.well-known/jwks.json` | Validate asymmetric access-token signatures. |
| `GET /api/v1/auth/me` and `GET /api/v1/auth/memberships` | Read the authenticated profile/membership choices through Identity-owned flows; never infer from client tenant data. |
| `POST /api/v1/auth/sessions/current-context` | Request a membership switch; Identity issues the replacement access token. |
| `POST /internal/v1/identity-users/resolve` | Exact, restricted lookup for an explicit academic link. |
| `GET /internal/v1/sessions/{sessionId}/status` | Optional online status/membership check for high-risk operations. |

Identity events may be consumed as integration signals, but they are not authorization proof. Consumers validate issuer, event ID, schema version, timestamp, replay/idempotency key, and current context before sensitive action.

## Data conventions

- JSON field naming is camelCase for Académico API contracts.
- Timestamps are ISO 8601 with explicit offset; storage uses the approved canonical timezone strategy.
- Enumerations are stable strings, not database ordinals.
- Pagination is cursor-based for potentially large collections; small bounded lists may use a documented page shape.
- Sort/filter capabilities are explicit per endpoint.
- Mutation endpoints document idempotency behavior.

## Error envelope

```json
{
  "error": {
    "code": "SUBMISSION_DEADLINE_INVALID",
    "message": "The submission could not be accepted.",
    "details": [],
    "requestId": "..."
  }
}
```

Messages should be safe for end users; diagnostic details belong in logs. Validation errors should identify fields without exposing internal schema, Identity secrets, account existence, or tenant data.

## Endpoint families

The exact route list belongs in the API contract, but the families are expected to include:

- tenant-scoped academic years, courses, students, teachers, Subject catalog entries, CourseSubjects, enrollments, assignments, and CourseSubjectTeacher relationships;
- learning units and typed learning items;
- file upload intents and metadata;
- submissions, reviews, and change requests, subject to later submission decisions;
- notifications;
- integration/sync status for authorized operators;
- explicit support operations that require the approved elevated context.

Upload control-plane requests use JSON metadata and return an opaque
`uploadIntentId` with an expiry and bounded upload instructions. File bytes use
the dedicated content endpoint as one-file `multipart/form-data`; bytes are not
embedded in JSON or represented as base64 in application contracts.

## Contract requirements

- A successful response and error response are documented.
- Authorization behavior is documented per endpoint.
- Cross-tenant, stale-context, revoked-membership, and lifecycle edge cases have tests.
- API changes are backward-compatible within a version or deliberately versioned.
- Provider-specific IDs are not required for normal client behavior.

## Pagination and idempotency baseline

Cursor-paginated collections use the conceptual envelope:

```json
{
  "items": [],
  "nextCursor": "opaque-value-or-null"
}
```

The cursor is opaque to clients and must not expose database IDs or ordering
implementation details. Idempotency is endpoint-specific; ordinary CRUD does
not automatically require `Idempotency-Key`. Uploads, submissions, and
synchronization may define stronger rules in their later accepted decisions.

## Unresolved API decisions

These do not change the reconciled Identity boundary:

- the internal encoding and signing/validation mechanics of opaque cursors;
- endpoint-level idempotency rules for academic uploads, submissions, and sync triggers;
- endpoint-level details for later submission revision/replacement behavior.
