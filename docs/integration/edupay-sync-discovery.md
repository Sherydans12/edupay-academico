Current manual mutation behavior matters for D-05:

- `createStudent` and `createTeacher` explicitly write `source = MANUAL`.

## Stable identifier and tenant findings

### Identifier rule

The safest proposed key is:

```text
(canonical tenantId, source = "EDUPAY", entityType, externalId)
```

For the current `Student` and `Teacher` tables, the exact target-side equivalent is:

```text
(tenantId, source, externalReference)
```

`externalReference` must contain the immutable source ID, not a name, RUT, email, course label, or display code. Names, RUT, and email may be search or reconciliation attributes only. If the source does not expose a stable immutable ID, no automatic synchronization is safe to accept.

For `Course`, `AcademicYear`, `CourseEnrollment`, and any future source entity, the target currently lacks the corresponding provenance field. This is a schema/contract gap to resolve in a later implementation decision; this discovery branch does not add it.

The source ID namespace must include the source entity type. A Student ID and Course ID with the same textual value must not collide; two records in the same source tenant with the same entity type and external ID must be rejected as a source data conflict.

### Tenant compatibility

Compatibility between an EduPay institution ID and the canonical ecosystem `tenantId` is **not proven**. The target evidence proves only that Académico uses the same canonical opaque tenant value as Identity in its own boundary. There is no source tenant record available to compare.

The required mapping is therefore:

```text
(sourceSystem = EDUPAY, sourceTenantId) -> canonical ecosystem tenantId
```

The mapping must be server-controlled, audited, and validated before any item is read or written. A client-provided `tenantId`, source tenant selector, record payload, email, or matching display name is not authorization context. If later evidence proves exact ID compatibility, the mapping may be an explicit identity mapping; it must not be assumed now.

### Local-edit conflict rule proposed for the MVP

The safe default is record-level source linkage, not fuzzy merging:

1. A source item with a new stable external ID creates a source-linked target record.
2. A target manual record is never selected by display name, RUT, email, or course label.
3. Source-authoritative fields on an already linked row may be updated by synchronization, with a per-field conflict result when the current local value differs.
4. Initial-only fields are written only when empty during initial linking; later source changes do not overwrite a local value.
5. Manual-only records are not changed by synchronization.
6. Because current audit does not retain before/after values, any accepted source-authoritative overwrite must be accompanied by sync item evidence sufficient for an operator to understand the change. If that evidence cannot be retained safely, the item must be held for review instead of silently overwritten.

This rule is intentionally conservative and remains subject to owner approval. It protects local administrative work without allowing mutable identifiers to become synchronization keys.

## D-06 — synchronization options

Direct database coupling is rejected as an MVP option. It would bypass the explicit service boundary, couple independent migrations and availability, expand tenant/credential exposure, and make source-side authorization and auditing ambiguous.

| Option | Complexity | Reliability and recovery | Load/latency | Deployment coupling | Security | Finding |
| --- | --- | --- | --- | --- | --- | --- |
| **A. Scheduled pull from EduPay API** | Medium; requires versioned API client and mapping | Strong retry and replay characteristics if pagination, stable IDs, and watermarks exist | Predictable bounded load; eventual consistency | Low-to-medium; source API contract is the dependency | Server-held service auth, tenant mapping, timeouts, and rate limits are explicit | **Recommended MVP, conditional on a supported API.** |
| **B. Scheduled pull from an explicitly supported export/interface** | Low-to-medium if a stable CSV/JSON export already exists; higher operational handling | Good for batch replay, weaker for partial changes/tombstones and freshness | Bursty load; latency is export interval | Lower application coupling, but operational export ownership is required | Secure delivery, integrity, tenant binding, and PII handling must be defined | Viable fallback only if source has no API and the export is an accepted contract. |
| **C. Push/webhook/event** | High for both producer and consumer; requires signed delivery, replay, ordering, and dead-letter behavior | Low latency, but requires durable delivery and reconciliation for missed events | Efficient steady-state load | High; source release and availability become coupled | Callback authentication, signature, audience, replay, and tenant checks are required | Not evidenced as available; future option. |
| **D. Hybrid push plus scheduled reconciliation** | Highest MVP complexity; two delivery paths and deduplication | Best eventual correctness if events are complemented by full reconciliation | Low latency plus periodic bounded load | High initially | Combines API and callback security surfaces | Recommended future evolution only after source capabilities are proven. |

### Recommended MVP mechanism

**Proposed MVP: Option A, scheduled pull from an explicit versioned EduPay API.** The pull should be tenant-scoped by server-side mapping, incremental when the source provides a trustworthy cursor or `updatedAt`, and periodically reconciled with a full source view. It should operate independently from interactive academic requests and fail without disabling manual Academic operations.

This is not an assertion that the current EduPay platform has such an API. If the missing source inspection proves that no supported API exists, the proposal must return to owner review; Option B may then be evaluated against a real export contract. No direct database adapter is proposed.

### Recommended future evolution

**Proposed future: Option D, push/events for low-latency changes plus scheduled full reconciliation.** Events would reduce propagation latency for student creation, enrollment moves, course changes, and deactivations, while the scheduled reconciliation remains the correctness backstop for missed, duplicated, or reordered events. This evolution is conditional on a source-owned signed event contract and durable delivery semantics.

## Frequency recommendation

Actual source behavior, change volume, source rate limits, and operational hours are unverified. Therefore no cadence is ready for acceptance.

The provisional operating baseline for an API-backed MVP is:

- hourly incremental pull while the institution is operational;
- one full reconciliation per day, preferably during a source-approved low-load window;
- a bounded operator-triggered run for onboarding or incident recovery, subject to the same tenant and authorization controls;
- no deactivation based on a failed, partial, or untrusted response;
- exponential backoff for temporary source unavailability.

This is intentionally not real time. The cadence must be changed before acceptance if source evidence shows a lower update rate, a stricter rate limit, no reliable watermark, or a business requirement for next-day rather than hourly freshness. The owner must approve the final cadence after source inspection.

## Idempotency and duplicate behavior

The proposed deterministic identity is:

```text
tenantId + source + entityType + externalId
```

The current target equivalent for Student and Teacher is:

```text
tenantId + source + externalReference
```

Rules:

- Use only an immutable source ID as `externalId`/`externalReference`.
- Require a non-empty source ID for a source-linked item; nullable provenance must not be used for synchronized rows.
- Scope IDs to the mapped source tenant and entity type.
- Upsert one item at a time or in small tenant-scoped transactions. A retry of the same item must produce the same target record and must not duplicate enrollment history.
- If the source supplies a version or `updatedAt`, ignore an older replay and treat an equal version/value as unchanged. Do not use a local `updatedAt` as a source ordering signal.
- Do not match by name, email, RUT, grade/section label, or any other mutable display value.
- Two source rows with the same `(source tenant, entity type, external ID)` are a source-data error. Quarantine both item results, do not choose a winner, and do not partially remap the key.
- A source ID already mapped to a different target record is a mapping conflict. Stop that item and require operator resolution; never silently move the external reference.
- A source response containing the same source ID under two tenants is rejected as a cross-tenant integrity error.
- A failed item does not roll back successful items in the same batch. The run records item-level failure and can safely retry the failed item.

For Course, AcademicYear, and relationship aggregates, the target has no current provenance fields. A future implementation must not pretend that the Student/Teacher uniqueness constraint is sufficient; the exact mapping key and history policy for each aggregate requires a reviewed contract and schema decision.

## Conflict and reconciliation behavior

The following behaviors are proposed and remain unaccepted:

| Case | Proposed behavior |
| --- | --- |
| Source changes a Student name | For a source-linked source-authoritative field, update the target and retain item-level conflict evidence when the local value differs. Do not affect a manual record that is not explicitly mapped. |
| Local administrator changes the same Student name | Do not fuzzy-merge. For a linked source-authoritative row, source wins only under the accepted field rule and the change is recorded; otherwise hold for explicit review. Initial-only/manual values remain local. |
| Student moves course | Deactivate the prior active `CourseEnrollment`, create or activate the new source relationship, and retain the old relationship and all learning/submission history. Require stable source relationship/course IDs. |
| Student becomes inactive | Transition `Student.status` to `INACTIVE` after a trusted source status change. Deactivate source-owned active course memberships as appropriate; preserve the student and evidence. |
| Course is renamed | Apply the source rename only to a source-linked source-authoritative course. Preserve the target internal ID and mapping; never identify a course by the new or old label. |
| Source record disappears | Treat absence as unconfirmed until a complete, successful reconciliation proves it. After an owner-approved absence grace rule (proposed: two consecutive successful full reconciliations), transition Student to `INACTIVE` or Course to `ARCHIVED`; never hard-delete. |
| Duplicate source IDs | Reject/quarantine the conflicting items and raise a reconciliation error. Never last-write-wins. |
| Partial batch failure | Commit successful item transactions, record failed item evidence, and retry only failed items. Do not mark the run fully successful. |
| Source temporarily unavailable | Preserve the last known state, mark the run failed or unavailable, back off and retry, and alert. Never deactivate records from an unavailable source. |

### Deactivation and history

Lifecycle transitions are required:

- `Student`: `ACTIVE -> INACTIVE`; retain the internal ID, source mapping, enrollments, learning access evidence, and submissions.
- `CourseEnrollment`: `ACTIVE -> INACTIVE` when a source-owned membership ends or a student moves; retain the historical relationship.
- `Course`: transition to `ARCHIVED` when a source course is confirmed gone or closed under the accepted source lifecycle rule; retain its year, course subjects, learning content, submissions, and mapping.
- `AcademicYear`: do not archive solely because one course disappears; its lifecycle remains governed by Academic policy unless the source contract explicitly owns the year.

No source event may overwrite Learning content or Submission originals. Student submission originals are immutable under the accepted storage decision, and synchronization must not hard-delete historical academic data.

## Reconciliation and observability proposal

The minimum operational evidence should be a tenant-scoped run summary and item-level errors. It should not be implemented in this discovery branch.

### `SyncRun` evidence

Proposed fields/values:

- run ID, canonical tenant ID, source (`EDUPAY`), mode, trigger, correlation ID;
- start/end timestamps and status (`RUNNING`, `SUCCEEDED`, `PARTIAL`, `FAILED`, `UNAVAILABLE`);
- source cursor/version or full-reconciliation marker when supplied by EduPay;
- last successful sync per tenant/source/entity type;
- counts: `seen`, `created`, `updated`, `unchanged`, `deactivated`, and `failed`;
- bounded error summary and retry state.

### `SyncItemResult` evidence

Proposed fields/values:

- run ID, source entity type, source external ID, mapped target ID when known;
- item result (`CREATED`, `UPDATED`, `UNCHANGED`, `DEACTIVATED`, `CONFLICT`, `FAILED`, `SKIPPED`);
- source version/updated timestamp, validation result, error code, and retryability;
- safe before/after field evidence only where required for conflict review, with PII minimized and redacted from ordinary logs.

The source cursor must be persisted only when the source defines its semantics. If no trustworthy cursor exists, use deterministic page traversal plus a successful full-reconciliation marker; do not invent a cursor.

## Security requirements

Source authentication details are unknown because the source checkout is unavailable. The accepted security baseline is:

- use a server-side source API credential, mTLS identity, or signed export/callback contract selected from source evidence;
- keep credentials in the deployment secret mechanism used by the integration runtime, never in source control, target database rows, client bundles, fixtures, logs, or these documents;
- validate source issuer/audience/signature/expiry where token-based, and validate callback signature, timestamp/replay protection, and payload schema where push is later accepted;
- resolve source tenant through the audited server-side mapping before reading or writing; do not authorize from a request `tenantId` or source payload selector;
- bound connect/read timeouts, retries, concurrency, page size, and rate; honor source rate limits and use a circuit-breaker/backoff behavior for outages;
- minimize copied PII to the approved academic fields. Do not synchronize credentials, password hashes, refresh tokens, activation secrets, payment details, or unapproved guardian data;
- redact names, RUT, email, tokens, and full payloads from ordinary logs. Use correlation IDs, source entity type, opaque external IDs, counts, and bounded error codes;
- require explicit tenant-admin/support authorization and audit for manual runs; `SYSTEM_ADMIN` has no automatic tenant access;
- isolate sync failure from interactive academic writes and recheck tenant/resource context for any asynchronous work.
